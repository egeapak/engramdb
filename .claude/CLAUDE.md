# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

EngramDB is a project-scoped persistent memory store for coding agents.
Tech stack: Rust (edition 2021), LanceDB (vector index), ONNX Runtime via `fastembed` / raw `ort` (all-MiniLM embeddings, cross-encoder reranker, NLI), MCP protocol via `rmcp`, Tokio.

The repo ships **one binary** (`engramdb`, `crates/engram-cli/src/main.rs`) that does everything — CLI, `serve` for the MCP server, `daemon` for the shared embedding host, `dashboard` for the local web view, and `hook` for Claude Code hook handlers. The same binary is what the Claude Code plugin in `.claude-plugin/` wires up.

This is a **Cargo workspace** (`[workspace] members = ["crates/*"]`). The per-layer crates under `crates/` are, in dependency order:

- `engram-types` — config + shared domain types (leaf, no heavy deps; `cargo check -p engram-types` is ~seconds).
- `engram-onnx` — `ort` execution-provider wiring (re-exported as `engramdb::onnx_ep`).
- `engram-storage` — `MemoryStore`, LanceDB index, paths/registry, telemetry (re-exported as `engramdb::storage` / `::telemetry`).
- `engram-models` — `embeddings` / `nli` / `title` providers.
- `engram-test-support` — the `#[ctor]` test-isolation arm (dev-only).
- `engram-mcp` — the `rmcp` MCP server surface; depends on the core.
- `engram-dashboard` — the local web dashboard (`engramdb dashboard`, axum; read-only except the opt-in `--allow-writes` edge review); a front end like `engram-mcp`, depends on the core.
- `engram-cli` — Clap CLI + the `engramdb` binary; depends on the core, `engram-mcp` and `engram-dashboard`.

The residual **core** is the top-level `engramdb` lib crate (`src/lib.rs`): `daemon`, `ops`, `prompt_intent`, `retrieval`, `scope`, `scoring`, `search`. It re-exports the extracted crates under their historical module paths (`engramdb::storage`, `::embeddings`, `::types`, …) so every `crate::<module>` / `engramdb::<module>` reference keeps resolving unchanged. **The dependency edges only point inward**: the extracted leaf crates must never `use` the core, and `engram-cli`/`engram-mcp`/`engram-dashboard` are front-ends that depend on the core (never re-exported from it — that would invert the DAG).

## Code Quality (mandatory)

Before marking ANY task as complete, you MUST run and pass both:

1. **`cargo fmt --all`** — format all code. Run this first.
2. **`cargo clippy --workspace --all-targets --all-features -- -D warnings`** — all clippy warnings are treated as errors. Fix every warning before proceeding.

Always pass `--workspace` so clippy/nextest cover every crate, not just the one in the current directory. No task is done until both commands succeed with zero warnings and zero errors. This applies to all agents and subagents. CI (`.github/workflows/ci.yml`) runs the exact same two commands plus `cargo nextest run --workspace --all-features`.

Feature flags from `Cargo.toml`:

- `onnxruntime` (default) — the ONNX Runtime stack (`ort` + `fastembed` + `engram-onnx`). With it off (`--no-default-features`), embeddings fall back to Ollama and NLI / reranking / T5 titling all compile out (ORT-only); keyword titling remains.
- **ONNX Runtime linking strategy** — `load-dynamic` (default) / `bundled-onnxruntime`. EngramDB no longer vendors a runtime; one of these decides where `libonnxruntime` comes from, and `load-dynamic` lives in `default`, so choosing the other requires `--no-default-features --features onnxruntime,ollama,bundled-onnxruntime`. `load-dynamic` `dlopen`s the runtime at *run* time (nothing needed at build time). **No release artifact contains a runtime in any form** — archives hold the binary only, and Homebrew/Scoop declare a dependency on the package manager's copy; the release notes carry the install instructions. `bundled-onnxruntime` downloads and statically links one (the pre-0.9 default — **avoid**: that prebuilt mis-executes quantized models on AVX-512/AMX hosts, see `docs/contributors/embedding-model-alternatives.md` R6/R9).

  **Build-time linking is deliberately not offered.** A `pkg-config` strategy (`ort/pkg-config`) would record `libonnxruntime` as a load-time dependency, and the dynamic loader resolves those before `main()` runs — so a missing runtime would stop the binary from starting at all, with no `doctor` output and no chance for the pre-flight probe to run. A CI step asserts the default binary has no ONNX entry in `ldd` and starts with no runtime installed; don't reintroduce one.

  Two consequences worth internalizing. **(1)** `--all-features` necessarily turns `bundled-onnxruntime` back on, so `cargo clippy/nextest --all-features` links a static ORT — but `load-dynamic` is *also* on (it is in `default`) and takes precedence at run time, so those runs still `dlopen` a **shared** library and still need `ORT_DYLIB_PATH`. Linking static does not exempt you; see the sandbox section. The `test-load-dynamic` CI job is what covers the no-`bundled` build. **(2)** Under `load-dynamic`, `ort`'s own loader **panics** when the dylib is missing, and the release profile is `panic = "abort"`, so it cannot be caught. `engram_onnx::runtime` therefore probes and validates the library with `libloading` *before* any `ort` call, and every model loader in `engram-models` calls `crate::ensure_onnx_runtime()` first. **Any new ONNX-backed loader must do the same**, or a user without the runtime gets a hard abort instead of the documented fallback to keyword search.

- `ollama` (default) — Ollama embedding backend via `reqwest`. Disable for pure offline ONNX.
- `coreml` (macOS only) — Apple Neural Engine EP for `ort` (implies `onnxruntime`).
- `xnnpack` — portable CPU-kernel EP for A/B benchmarking (implies `onnxruntime`).

### CLI snapshot tests (insta)

CLI output is pinned by `insta` snapshots in two tiers. Full guidance is in `docs/contributors/testing.md`; the parts worth knowing before you touch CLI output:

- **Tier 1 — renderers** (`crates/engram-cli/src/output.rs::tests`, snapshots in `crates/engram-cli/tests/snapshots/renderer/`). Every `OutputFormatter::print_*` × `pretty`/`json`/`plain`, driven in-process from fixtures with pinned ids and pinned clocks, so the snapshots hold the **real bytes with no redaction**. Layout changes belong here.
- **Tier 1.5 — the command tier** (`tests` modules in `crates/engram-cli/src/commands/*.rs`, harness in `src/testutil.rs`, snapshots in `crates/engram-cli/tests/snapshots/command/`). Runs a handler in-process against a real store in a temp dir with a scripted `MockPrompter` and a capturing formatter — the only tier that reaches an interactive flow (tier 1 has no store/prompter; tier 2's `inquire` wants a TTY and cannot see `#[cfg(test)]` lib items). `MockPrompter` records *what it was asked*, so prompt wording and option lists — which reach the terminal via `inquire`, never the formatter — finally get asserted. Use `TempProject` / `capturing_plain()` / `interaction()` / `snap_command()`; names must be command-prefixed and unique, since `snap_command` disables insta's module prefix (insta derives it from the asserting file, so everything would read as `testutil`).
- **Tier 2 — the binary** (`crates/engram-cli/tests/cli/snapshot/`). Spawns `engramdb` and snapshots command line + exit code + stdout + stderr. Exit codes, stream routing, and clap's exit-2 errors are only reachable here. Note `doctor --fix`'s prompt is gated on `std::io::stdout().is_terminal()` read directly, so its *interactive* branch is unreachable from every tier; only the no-TTY and `--yes` branches are testable. The `$EDITOR` flows (`add -e`, `update -e`) live here in `snapshot::editor`, `#[cfg(unix)]`, driven by a `#!/bin/sh` fake editor the fixture writes into the project root (so `[PROJECT]` redacts its path); `Fixture::run_with_editor` sets `EDITOR` for just those cases, because `base()` removes it and every other test depends on that.
- **The `projects prune` progress bar** (`crates/engram-cli/src/progress.rs`). `indicatif` draws to the real stderr and `is_hidden()` is `!term.is_term()`, so it renders nothing under a pipe — invisible to tier 2, and to the command tier too since the bar never touches the formatter's sink. `make_bar` therefore takes the `ProgressDrawTarget` as a parameter and tests pass an `InMemoryTerm`. **`indicatif`'s `in_memory` feature must stay a dev-dependency**: it pulls in `vt100`, and only resolver v2 (this workspace is non-virtual, edition 2021) keeps that out of the shipped binary — verify with `cargo tree -p engram-cli -e normal -i vt100`, which must print nothing. The `{eta}` in the template is wall-clock derived but pins at `0s` (indicatif returns `Duration::ZERO` when no samples exist, and adjacent ticks make `sps` enormous); `progress_eta_is_stable_across_renders` guards that, and names the redaction to add if it ever fires.

`OutputFormatter` writes through a `Sink` (`Stdout`/`Stderr` in production, `Capture` under `#[cfg(test)]`) rather than calling `println!` directly — that seam is what makes tier 1 possible, because a snapshot needs the rendered bytes as a *value* and `println!` sends them where no in-process test can read them. **All CLI output goes through `outln!` / `errln!` / `outraw!` / `errraw!`** (`use crate::output::{outln, …};` — they are `pub(crate) use`d, not `#[macro_use]`d, because `mod commands` precedes `mod output` in `lib.rs` and `#[macro_use]` is textually ordered). The `formatter-output` CI job fails the build on a bare print macro anywhere in `crates/engram-cli/src`. Exactly two exemptions, both deliberately outside the formatter: `output.rs` defines the macros, and `commands/hook.rs` emits the hook protocol document Claude Code parses off stdout (plus `warn_unknown_hook`, moved there from `lib.rs` so the whole raw-output surface is one file). `#[cfg(test)]` bodies are skipped — but match the real `mod tests {` opener, not the first `#[cfg(test)]`, since `hook.rs` carries that attribute on helper fns hundreds of lines earlier.

**Colour is tier 1 only**, via `snap_colored` (Pretty) / `assert_never_styled` (the deliberately-colourless renderers). Getting an escape out under a test runner needs both `capturing_colored()` (clears the formatter's `use_color`) and `owo_colors::with_override(true, …)` (short-circuits `if_supports_color`, which otherwise probes the real stdout); the helpers do both and assert escapes were/weren't produced. Snapshots store readable tags — `ansi_to_tags` turns `\x1b[32m✓\x1b[39m` into `<green>✓</green>` — so never write a raw escape into a `.snap`. Tier 2 stays colourless by construction: `OutputFormatter::new` checks `is_tty` itself, so no env var can force styling into a pipe. **Gate styling on `self.styled()`, not `self.use_color`** — `use_color` excludes only Json, so a shared Pretty/Plain code path that reads it directly styles Plain output on a terminal (`print_project_list` did).

Regenerate with `cargo insta test --accept --test-runner nextest`, review with `cargo insta review`; never hand-edit a `.snap`. Under CI insta refuses to write, so a drifted snapshot fails rather than passing silently. **Always re-run a snapshot suite twice** — non-determinism only shows on the second run.

Two hazards the harness already handles, worth not reintroducing: id-redaction regexes must not use `\b` (ids sit inside filenames, and `_` is a word character), and model-backed subsystems are disabled in `fixture_config()` rather than assumed absent (CI installs an ONNX runtime; a developer box may not).

### Nextest test groups

`.config/nextest.toml` puts ONNX-model-loading tests (`nli::onnx::tests::*`, `embeddings::onnx::tests::*`, `retrieval::engine::tests::test_rerank`, `test_search_with_real`) in the `ml-models` group with `max-threads = 1`. Don't parallelize these — they share heavyweight model state.

### Test isolation

The `engram-test-support` crate provides the `#[ctor::ctor]` arm that points `ENGRAMDB_DATA_DIR` and `ENGRAMDB_CONFIG_DIR` at per-process temp dirs so tests never touch the real `~/Library/Application Support/engramdb/` or registry. Each crate's test build links it (the core's `src/lib.rs` calls `engram_test_support::arm()` under `#[cfg(test)]`; downstream crates pull it in as a dev-dependency). Nextest's process-per-test model is load-bearing here — `cargo test` would not isolate these globals correctly.

The **model cache** is separate from the data dir and is *not* redirected by the `#[ctor]` arm (model-loading tests need the real shared cache). Two env vars (both resolved in `engram_storage::paths`) make model *presence* deterministic for the tests that assert a model is missing/available:

- `ENGRAMDB_MODEL_CACHE_DIR` — overrides `model_cache_dir()` (mirrors `ENGRAMDB_DATA_DIR`). Point it at an empty temp dir to simulate an unstaged cache.
- `ENGRAMDB_OFFLINE` (truthy: `1`/`true`/`yes`/`on`) — makes the embedding/NLI/T5 loaders refuse to download an uncached model, failing fast instead. An empty cache alone is *not* enough on a networked machine (fastembed would just download); pair it with offline. Example: `stats_embeddings_status_onnx_backend_model_missing` sets both so it passes regardless of what the developer has cached.

Note: `cargo test --lib` has two pre-existing flaky failures under full parallelism (`ops::doctor::tests::test_doctor_many_memories_healthy`, `ops::projects::tests::test_get_project_info_with_memories`) — they pass in isolation and fail identically on a clean base, so they are not a regression signal.

Note: `mcp::server::tests::global_retrieve_with_semantic_query` and `reindex_re_embeds_in_error_mode_despite_mismatch` were similarly flaky under a full-parallel `cargo nextest run --all-features` (sandbox AND coverage-instrumented CI); both are now serialized in the `ml-models` nextest group. The daemon path is disabled under `#[cfg(test)]`, so every embedding test loads ONNX in-process; when many processes lose the model-load race at once, the embedding provider resolves to `None`, the memory is stored without a vector, and the semantic query returns empty. It passes in isolation and on adequately-resourced CI, so it is not a regression signal.

### Fuzzing

`fuzz/` is a standalone `cargo-fuzz` crate (its own `[workspace]`, excluded from
default builds). Targets live in `fuzz/fuzz_targets/` and exercise code that
consumes untrusted input — either hand-written parsers or score math whose
inputs originate from on-disk memory files:

- `memory_file` / `memory_file_roundtrip` — TOML/YAML frontmatter + V2 markdown
  via `storage::memory_file::parse_memory_file` / `write_memory_file`.
- `scope_logical` / `scope_physical` / `scope_proximity` — dot-notation LCA math,
  runtime glob compilation, and the top-level physical+logical combiner. All
  assert the score is finite (the [0,1] bound only holds for config-validated
  decay constants, which the fuzzer doesn't respect).
- `decay` — `scoring::decay_factor` age/TTL/half-life arithmetic; asserts a
  finite factor for arbitrary durations and timestamps (finite floor only).
- `registry` — the global `registry.json` (user-writable, read on every
  command) via `serde_json` into `storage::registry::Registry`, then the pure
  hierarchy walks (`resolve_root_project_id`, `collect_descendants`); asserts
  no panic and bounded/cycle-safe traversal.
- `slug` — the filename helpers (`slugify`, `extract_id_from_stem`,
  `stem_matches_id_prefix`) over arbitrary titles/stems; asserts no panic and
  the documented slug bounds (a non-char-boundary slice on multibyte titles
  once panicked here).
- `composite_score` — the core ranking formula; asserts `final_score` is always
  finite even for `NaN`/`inf` criticality (parsed from files via `f64::parse`),
  with the graph/usage terms fuzzed too (arbitrary `ScoreSignals`, usage
  counts up to `u64::MAX`, unvalidated `contradicts_penalty` /
  `supports_boost` / `usage_weight`).

Each target only calls already-`pub` pure functions — no API was widened for
fuzzing. If the surface you want to fuzz is behind a private `mod`, prefer an
existing public entry point that exercises it transitively (e.g. the field
parsers in `storage::memory_file::helpers` are covered through
`parse_memory_file`) rather than making the module `pub`.

**Adding a target:** create `fuzz/fuzz_targets/<name>.rs` *and* register a
matching `[[bin]]` block in `fuzz/Cargo.toml` with `test/doc/bench = false` —
`cargo fuzz build` (no target arg) builds every `[[bin]]`, so a block pointing
at a missing file, or a target file with no block, breaks the whole build.
Drive the target from libfuzzer's `Arbitrary` inputs (tuples of
`String`/`Vec`/`Option`/`i64`/`f64`/`u8` all work out of the box) and construct
domain types from those primitives in the body. For score math, assert the
weakest invariant that must always hold — `is_finite()` — because the fuzzer
ignores config validation; only assert tighter bounds like `[0,1]` when you
first clamp/guard the inputs into their valid domain (see the `floor` guard in
`decay.rs`). When a degenerate input (e.g. a literal `NaN` config field) is an
input-validation concern rather than the arithmetic under test, `return` early
on it so the assertion stays meaningful.

Run with `cargo +nightly fuzz run <target> -- -max_total_time=60`. In the web
sandbox, building requires the same `ORT_STRATEGY=system ORT_LIB_LOCATION=/tmp/ort-lib`
workaround below. A full `fuzz/target` is ~14 GB on top of the main `target`, so
on the web sandbox watch `df -h` and reclaim space with `rm -rf fuzz/target`
(and `cargo clean`) if a build fails with `No space left on device`. Seed inputs
are committed under `fuzz/corpus/<target>/`; the `.gitignore` keeps only curated
`*.md` seeds (the auto-grown binary corpus is ignored). When a crash is found,
commit the failing input from `fuzz/artifacts/` as a new corpus seed so it
becomes a permanent regression case. CI runs these on a schedule via
`.github/workflows/fuzz.yml`, not on every PR.

## Building & testing in Claude Code on the web (restricted egress)

The web sandbox's egress gateway uses a custom CA that rustls/webpki-based downloaders (the `ort` build script, `hf-hub`) reject, even though `curl` works (it trusts `/etc/ssl/certs/ca-certificates.crt`). Cold builds/tests fail without these one-time workarounds:

1. **protoc** (LanceDB build dep): `apt-get install -y protobuf-compiler`.
2. **ONNX Runtime binary.** Two separate needs now, because the runtime is no longer compiled in:

   - *Building* `--all-features` (which CI and the commands above use) still enables `bundled-onnxruntime`, so `ort-sys` still wants a static lib to link and its download still fails with `UnknownIssuer`. The `ORT_STRATEGY=system ORT_LIB_LOCATION=/tmp/ort-lib` workaround below is unchanged.
   - *Running* needs a **shared** library — including under `--all-features`. `load-dynamic` is a *default* feature, so `--all-features` turns on `bundled-onnxruntime` **as well as**, not instead of, `load-dynamic`; the static lib is linked but never used, and the runtime is still `dlopen`ed. So a `--all-features` test run needs a `.so` exactly as much as a default build does, and the static `ORT_LIB_LOCATION` alone is not enough. Export `ORT_DYLIB_PATH=/path/to/libonnxruntime.so`, or drop the `.so` next to the binary — `engram_onnx::runtime` searches the executable's directory first. `engramdb doctor` reports which one it resolved.

     Missing it looks like a *model* problem, not a runtime one: `OnnxProvider::try_new()` returns `None` and the same ~20 tests listed in §3 below fail identically. If those tests fail, verify **both** the `.so` and the staged model before blaming either.

     The pyke prebuilt (below) ships only `libonnxruntime.a`, so it cannot satisfy this. Fetch the official archive for the `.so`:
     ```
     cd /tmp && curl -sSLO https://github.com/microsoft/onnxruntime/releases/download/v1.24.2/onnxruntime-linux-x64-1.24.2.tgz
     tar -xzf onnxruntime-linux-x64-1.24.2.tgz
     export ORT_DYLIB_PATH=/tmp/onnxruntime-linux-x64-1.24.2/lib/libonnxruntime.so
     ```

     A full green sandbox run therefore needs BOTH: `ORT_STRATEGY=system ORT_LIB_LOCATION=/tmp/ort-lib` (build) and `ORT_DYLIB_PATH=…/libonnxruntime.so` (run).

   Fetch + decode the prebuilt static lib via curl, then build with `ORT_STRATEGY=system ORT_LIB_LOCATION=/tmp/ort-lib`. The version must provide the C API the locked `ort` crate is built for (`2.0.0-rc.13` with `api-24` → ONNX Runtime ≥ 1.24 / API 24); a mismatch surfaces at *runtime* as "The requested API version [N] is not available". If you swap the lib after a build, also `rm -rf target/debug/build/ort-sys-* target/debug/.fingerprint/ort-sys-* target/debug/deps/*ort_sys*` — the objects are bundled into the ort-sys rlib at its build time, so relinking alone keeps the old runtime:
   ```
   curl -sS -o /tmp/ort.tar.lzma2 "https://cdn.pyke.io/0/pyke:ort-rs/ms@1.24.2/x86_64-unknown-linux-gnu.tar.lzma2"
   python3 -c "import lzma; open('/tmp/ort.tar','wb').write(lzma.decompress(open('/tmp/ort.tar.lzma2','rb').read(), format=lzma.FORMAT_RAW, filters=[{'id':lzma.FILTER_LZMA2,'dict_size':1<<26}]))"
   mkdir -p /tmp/ort-lib && tar -xf /tmp/ort.tar -C /tmp/ort-lib
   ```
   Export `ORT_STRATEGY=system` and `ORT_LIB_LOCATION=/tmp/ort-lib` for all `cargo build/clippy/test` commands.

   ⚠️ **The pyke prebuilt executes quantized models incorrectly on AVX-512/AMX
   hosts.** Under CPU contention the same text embeds to unrelated vectors
   (measured: 44/60 distinct embeddings of one string; cosine below 0). It is
   the *build*, not the version or the model — Microsoft's own 1.24.2 release is
   bit-reproducible for the identical files. For any work that depends on
   embedding values (quality benchmarks, reproducibility checks), link the
   official runtime instead:
   ```
   curl -LO https://github.com/microsoft/onnxruntime/releases/download/v1.24.2/onnxruntime-linux-x64-1.24.2.tgz
   tar -xzf onnxruntime-linux-x64-1.24.2.tgz
   export ORT_STRATEGY=system ORT_PREFER_DYNAMIC_LINK=1 \
          ORT_LIB_LOCATION="$PWD/onnxruntime-linux-x64-1.24.2/lib"
   # binaries then need LD_LIBRARY_PATH="$ORT_LIB_LOCATION" at run time
   ```
   See `docs/contributors/embedding-model-alternatives.md` (R6/R9).
3. **Embedding model** (fastembed download fails the same way): since #77 the default is the **uint8** `DEFAULT_ONNX_EMBEDDING = ONNX_ALL_MINILM_L12_U8` — **L12, not L6**, repo `Xenova/all-MiniLM-L12-v2`, file `onnx/model_uint8.onnx` (~33 MB). Stage it into `~/.cache/engramdb/models/models--Xenova--all-MiniLM-L12-v2/` with `refs/main` containing `main` and `snapshots/main/<file>` for `onnx/model_uint8.onnx`, `tokenizer.json`, `config.json`, `special_tokens_map.json`, `tokenizer_config.json` (curl from `https://huggingface.co/<repo>/resolve/main/<file>`). `hf-hub` serves cached files without any network call, so embedding tests then pass offline. Other providers (`all-minilm-l6`, `all-minilm-l12-fp32`, the legacy `*-int8` specs) need their own repo staged the same way — check the spec's `hf_override` in `crates/engram-models/src/embeddings/onnx.rs` for the exact repo/file rather than assuming.

   ⚠️ Staging the *wrong* MiniLM repo is indistinguishable from staging none: `OnnxProvider::try_new()` returns `None`, embeddings appear unavailable, the `Auto` backend silently falls back to Ollama (unreachable in the sandbox), and ~20 tests fail — `ops::tests::expected_fingerprint_matches_live_default_provider` with "default ONNX model available in test env", plus most of `update::*`, `reindex::reindex_embeddings_only`, and `stats::stats_embeddings_status_all_minilm_available_via_onnx`. A pre-#77 cache (L6 `model_quantized.onnx`) fails exactly this way, so re-check this section against `DEFAULT_ONNX_EMBEDDING` before concluding those tests are a pre-existing repo failure.
4. **T5 title model** (master makes `title.strategy = "t5"` the default; same download failure): pre-stage `DEFAULT_T5_MODEL = T5_XENOVA_Q` (repo `Xenova/t5-small`) into `~/.cache/engramdb/models/models--Xenova--t5-small/` with `refs/main` → `main` and `snapshots/main/<file>` for `onnx/encoder_model_quantized.onnx`, `onnx/decoder_model_quantized.onnx`, `tokenizer.json`. Without it, `create`-path title generation can't build T5.

## Architecture

### Layered structure

The codebase is layered so that CLI and MCP share one operations core:

```
CLI (engram-cli)  ─┐
                 ├─► ops (src/ops/) ─► retrieval (engine) ─► storage (MemoryStore + LanceDB)
MCP (engram-mcp)  ─┘                  └─► scoring  ─► scope
                                   └─► embeddings / nli / retrieval::reranker
```

- **`src/ops/`** — typed input/output for every memory operation (`create`, `query`, `update`, `delete`, `challenge`, `gc`, `compress`, `reindex`, `doctor`, `stats`, `projects`, `harvest`, `harvest_index`, …). No CLI formatting, no MCP serialization. Both surfaces call into this same code.

  `ops::harvest_index` is the conversation-search policy layer. Everything it *persists* is bounded and defanged on the way in — `cwd` / `git_branch` / `first_prompt` through `harvest::defang_metadata` (`MAX_META_CHARS`), the curated summary through `harvest::defang_prose` (`MAX_SUMMARY_CHARS`, applied before the embedding call so the model time is bounded too). Nothing below `MAX_RECORD_BYTES` (4 MiB *per field*) bounds a transcript record, and a row is written once and replayed on every hit. Its embedding input is **not** the agent-facing digest render: that render draws a fresh random fence token per call (so recorded content cannot forge the framing) and prefixes a constant trust header, and neither belongs in a vector — the token would make the vector different on every run, breaking `reindex --archive-only`, and the header is identical boilerplate in every row. `ops::harvest::index_text` renders the same events through the same `defang` pipeline without either. The parse profile is `ParseOptions { tools: ToolDetail::FailuresOnly, .. }`: successful tool calls dilute the vector, failures and their error text are frequently the whole durable lesson. `ToolDetail::FailuresOnly` has to be applied **after** the whole transcript is walked, because a call's outcome only arrives with its `tool_result` record several records later.

  **Harvest terminology** — four different things, two of which are JSONL: the **ledger** is our state log (one line per session: id, stage, decision, timestamps, memory ids, pointer to the copy — *no conversation content*, bytes per session); the **transcript copy** is the conversation itself, copied out of `~/.claude/projects/` before Claude Code prunes it (~1–3 MB/session); the **digest** is the deterministic, code-generated reduction an agent reads (~60 KB/session); the **index row** is summary + embeddings in LanceDB (~KB/session). "Archive" is retired as a noun — it meant both the copy and the compressed stage. Say **transcript copy** for the bytes and **compressed** for the stage.

  Indexing is driven from `ops::maintenance` with two triggers, not one: a session a human settled is due at once, and a session **nobody** reviewed is due once it is older than `[harvest] index_after_hours`. Drop the second and search only ever finds what you already read.

  **A row and its ledger entry come apart routinely, so every path has to converge.** `harvest reset`, `harvest_mark clear=true`, `ledger rm` and the ledger's own 365-day window all drop an archive-less entry while its `conversations` row survives — no failed write involved. So the `IndexAction::Unchanged` path writes the `Indexed` stage too (one appended line, once); without it `doctor` reports an indexed session as "due for indexing and not yet searchable" forever and every maintenance pass re-locates, re-parses and re-hashes its transcript. The other direction is `forget_session`: deleting a conversation has to take the row, because it holds `first_prompt` and the curated summary *verbatim* and nothing ever revisits a session with no bytes left. `--archive-only` deliberately keeps the row (it retracts nothing, and the summary is unrecreatable); a full `ledger rm` deletes it.

  `Prefer::{Live,Copy}` in `locate` is not an optimization knob: `reindex --archive-only` reads the **stored copy** even when a live transcript exists, because that command's whole purpose is to demonstrate the copies are sufficient. Reading live-first made the documented behavior false in the one way that stays invisible until the transcripts are gone.

### Storage (`crates/engram-storage/src/`, crate `engram-storage`, re-exported as `engramdb::storage`)

- **`MemoryStore`** (`store.rs`) is the orchestrator. Memories live on disk as TOML-frontmatter markdown files in `.engramdb/memories/`. A single LanceDB table (`lance_index.rs`) holds both metadata-for-filtering and (optional) embedding vectors — there is no separate metadata DB.
- **Schema migration (`manifest::CURRENT_SCHEMA_VERSION`, currently `0.9.0`).** The memories-table column set is versioned in the manifest. `MemoryStore::migrate_schema_if_needed` runs on every store open (`init`/`init_global`/`open_global`): when the recorded version is behind, it reindexes (rebuild the memories table from the `.md` files — seconds, vectors preserved, no re-embed) and stamps the current version. New stores are born current. Adding a memories-table column ⇒ bump `CURRENT_SCHEMA_VERSION` so existing stores backfill on open. The `decay` (JSON `Option<Decay>`) and `has_embedding` columns were added this way (R2/R3); `has_embedding` mirrors chunk-table presence and is maintained via `LanceIndex::{has_chunks,set_has_embedding}` on the write path. The 0.3.0 bump added the seven epistemic columns (`epistemic`, `verified_at`, `generality`, `origin_task`, `valid_from`, `invalidated_at`, `watch_paths`); see `docs/contributors/architecture.md` ("Epistemic classes and bi-temporal validity"). The 0.6.0 bump is different in kind: it added a whole new **table** (`conversation_index.rs`'s `conversations`) rather than a memories-table column, so the migration it triggers rewrites nothing — it exists only so a store created before the table gets one. The 0.8.0 bump added `content_sha256` / `content_len` (what bytes a row was built from) and, on the chunks table, `embed_sha256` (what a memory's vectors were embedded from). The 0.9.0 bump added the derived `edges` **table** (see "Memory edges" below); a test builds a real 0.8.0 store by dropping it (`store::tests::downgrade_to_0_8_0`). The 0.7.0 bump added `source_sessions`, the harvest evidence link (the sessions a memory was extracted from, which also pins their transcript copies against eviction — see "Harvest provenance and pinning" below). Because the migration rebuilds the memories table **from the `.md` files**, any relation that must survive it has to be *in* those files: that is why provenance is a field on the memory rather than a join table, and why a test builds a real pre-0.7.0 table (`store::tests::downgrade_to_0_6_0` strips the column from the live Arrow schema) rather than only downgrading the manifest stamp.
- **Memory edges (`engram_types::link`, `crates/engram-storage/src/edge_index.rs`, policy in `src/ops/links.rs`).** A memory's **outbound** typed edges (`contradicts`/`related_to`/`duplicates` symmetric, `supports`/`derived_from`/`supersedes` directed; `origin`, `status` proposed|confirmed|rejected, `confidence`, `store`, `at`, `note`) live in `Memory::links`, i.e. the `.md` hidden block — a field, not a join table, for the same two reasons as `source_sessions`. Unknown kind/origin/status parse into `Other(String)` and round-trip verbatim; never collapse that into a closed enum, or a newer binary's edge is erased on the next `update`. The per-store `edges` LanceDB table is **derived**: rebuilt by `reindex`, maintained under the write lock on every write path (`sync_edges_locked` after each index upsert, `delete_edges_locked` on delete), rows owned by the declaring file (`owner_id`, replaced in one `merge_insert`), `supersedes`/`superseded_by` mirrored in as `supersedes` rows (those fields stay canonical; a `links` entry of kind `supersedes` is emitted only while the field still lists its target). **Its write failures warn and never fail the memory write** (the `.md` is already on disk; failing made a retried create duplicate) — `doctor` reports `table_drift` and `reindex` rebuilds it. A write whose memory had and has no edges commits nothing (`owns_any` read first: Lance versions a no-match delete); `optimize` compacts the table. Reads never create the table — a missing table is "no edges" — and nothing creates it until a store has an edge. A same-store symmetric edge is keyed on its sorted endpoints (`EdgeRow::edge_key`), so two concurrent opposite links fold into one. **There is deliberately no `MemoryUpdate` field for links**: every edge write is an add/remove of *one* edge through `update_with`, because a wholesale list replacement from a snapshot read erases a concurrent writer's edge. Rules (module docs of `ops::links`): a symmetric edge is stored once and seen from both ends; a re-link changes only the fields passed and a **proposal never touches an existing edge** (re-proposing would downgrade a confirmed edge, revive a rejected one, overwrite the reviewer's note); `supersedes` exists only as confirmed (`link`/`set_link_status` refuse other statuses; rejecting one = `unlink`, which reopens the target only if no other memory still supersedes it); a committed (project-store, shared) file never names a personal memory **in any direction**, checked before any write by `ops::links::check_privacy` from `link`, `create`, and `update` (visibility or supersedes changes, including shared → personal while a shared file names the memory) — symmetric edges flip to the personal side, everything else is refused, and `doctor`'s leak check runs on the **un-deduplicated** rows (dedupe folds the `superseded_by` mirror, which is the copy in the other file); dangling is legal (delete leaves inbound edges, reads hide them, doctor's "Memory edges" check warns); a cross-store target whose store will not open is `Unknown`, never `Dangling`; `compress` moves sources' outbound edges onto the summary; edges are not challenges (`resolve keep` leaves them) and `gc` never edits them. `confirm_contradiction_direction` is the one reviewer verdict on a `contradicts` edge (both stand / `winner` supersedes loser, recording `resolved` on the loser / reject-and-keep); the winner path refuses a loser another memory already superseded. `set_link_status` (and the review paths) update **both** stored copies of a symmetric edge — a hand-edited or pre-dedupe pair can exist in both files, and updating one left the edge reading proposed from the other end; `dedupe`/`status_rank` folds any remaining pair Confirmed > Rejected > Proposed, so a rejection is never shadowed by a proposal. **Automatic proposals** (`src/ops/link_proposals.rs`, `[links]` = `LinksConfig`): NLI contradictions become proposed `contradicts` edges (`origin: nli`, the NLI score as confidence) and embedding neighbours proposed `related_to` (≥ `related_threshold`), `origin: similarity`, or `duplicates` (≥ `duplicate_threshold`) **only when NLI ran on the pair and cleared it** (`IngestFindings::nli_cleared`; near-identical vectors can still contradict, and "duplicate" invites a delete). The detection stays in the engine and makes **no model call of its own**: the search vector is the unit mean of the chunk vectors the memory was just embedded with (`embed_memory_with` returns it; `embed_for_ingest` on the sync path), then **one** vector search for both NLI and similarity, over-fetched so dropping self and invalidated neighbours still leaves `similar_candidates` — but the *edge writes* happen in `ops`, through an `IngestFollowUp` closure that `ops::create`/`ops::update` hand to `spawn_ingest` (the engine and `engram-models` must never `use crate::ops`). The sync create path runs `apply_ingest_findings` inline. Rules: any existing edge between the pair (any kind, any status, rejected included) blocks a proposal, so a rejected edge is never re-proposed; `max_proposals_per_memory` caps *pending* `nli`/`similarity` proposals on **both** ends, contradictions taking slots first, counting only proposals whose other end is live (a gone or invalidated end frees its slot; concurrent creates can overshoot — declared in the module docs); personal-side placement is `link`'s own rule; each write records `linked` with `Surface::Maintenance`; never on a hook path. Proposed edges change no score. `challenge --against` runs `check_link` (all of `link`'s checks, no write) before recording the challenge, so a bad target fails the whole call. Phase-4 readers use `links_of` / `load_graph` / `edge_health`, all side-effect free. **A malformed hidden block is an error, never a reset**: an unclosed, unparseable or merge-conflicted block fails `parse_memory_file` (`get`/`update` refuse; `doctor` lists it as `unparseable` and fails the store check) — it used to parse as "no hidden fields", and the next rewrite silently erased visibility, supersession, challenges and links. **And it must never cost the memory its index**: `reindex_with` parses every file before touching the table, recovers an unparseable file's id (`memory_file::recover_id`: frontmatter, then filename stem), carries its row across the clear (`LanceIndex::snapshot_rows`/`restore_rows`, conformed to the current schema — a non-nullable column the snapshot lacks is the one declared loss, warned), counts it in `indexed_ids` so neither the deletion reconciliation nor the orphan-chunk prune takes its row or vectors, keeps the edge rows it owns, and reports it in `ReindexCounts::unparseable` → `ReindexResult` (CLI warning, MCP `unparseable`). Dropping it made a merge conflict delete the memory, its vectors and its harvest pins on the next reindex, including the forced migration one.
- **Concurrency:** mutating ops acquire a per-project advisory `flock(2)` (`write_lock.rs`); reads are lock-free and rely on LanceDB MVCC. File writes are atomic temp-then-rename.
- **Paths (`paths.rs`)** resolve platform dirs via the `dirs` crate. Project-local data lives in `<project>/.engramdb/`; **personal** memories and LanceDB indices live in `<global_data_dir>/projects/<id>/{personal,lancedb}/`. `ENGRAMDB_DATA_DIR` and `ENGRAMDB_CONFIG_DIR` override these (the test harness uses them).
- **`project_id.rs` / `registry.rs`** — every project gets a 16-char SHA-256-derived ID; a global `FileRegistry` tracks them. The well-known global store ID starts with underscores so it cannot collide.
- **`transcripts.rs` / `transcript_archive.rs` / `harvest_state.rs`** — the harvest triad, read-only foreign state in the same category as the registry. `transcripts.rs` locates and parses Claude Code's own JSONL session logs under `~/.claude/projects/<encoded-cwd>/`, honoring **`CLAUDE_CONFIG_DIR`** (the one foreign env var this codebase reads) and normalizing them to an `Event` stream; the encoded directory name is a *lossy fast path only* — the `cwd` recorded inside each record decides attribution, because a wrong one feeds another project's conversations into this store. Budgeting, markdown defanging, and rendering are policy and live in `src/ops/harvest.rs` (terminal-escape sanitization is `sanitize_for_terminal` here in storage; `ops` only calls it); storage stops at the normalized stream and must never depend back on `ops`. `transcript_archive.rs` writes the zstd copy the SessionEnd hook takes, at `<global_data_dir>/projects/<root_id>/transcripts/` — **never** under `.engramdb/`, which is repo-adjacent and gets committed. **The copy is verbatim**: nothing is stripped at collect time, because (a) it is evidence — a challenged memory must resolve to what was actually said — and (b) you cannot un-drop. Reduction at collect would cap `reindex --archive-only` at reduction v1 forever; a whole copy keeps every later improvement (better summarizer, different chunking, changed tool heuristics) one re-derivation away. Reduction is a *projection per consumer*, never a mutation of the stored copy. `prune_archives` takes the pinned set as a parameter and never computes it — storage must not depend on `ops`; see "Harvest provenance and pinning". `harvest_state.rs` is the per-project ledger at `.engramdb/state/harvest_ledger.jsonl` — kept on the **root** project and shared not only with its git worktrees but with every sub-project linked under it by `engramdb projects link`, since those projects are offered each other's sessions and prune each other's copies. A ledger found at a sub-project's own path (written before it was linked) is **auto-adopted**: `adopt_ledger` appends its lines to the root's on the next harvest command there and renames the original to `harvest_ledger.jsonl.adopted`. Moving it aside is what commits the adoption, so a sub-project directory that cannot be written to adopts nothing (warning, naming the path) rather than re-appending the same entries on every command — which would undo a `harvest reset` each time. It is an **append-only JSONL log**, not a map: one line per state transition, each line a *patch* (absent field = unchanged, `null` = cleared), folded in **timestamp** order so last-write-wins is per field. That is what lets the SessionEnd hook write with one `open`+`write` and no lock, and it is why there is no `flock`, no merge-precedence function and no corrupt-file quarantine — don't reintroduce them. Every read *and* write of a file under `.engramdb/state/` goes through `state_file.rs`, never `std::fs`: those opens carry `O_NOFOLLOW` (a committed symlink at one of these paths is an arbitrary-file read whose bytes `adopt_ledger` copies verbatim into the root's log) plus `O_NONBLOCK` and a regular-file check (`O_NOFOLLOW` does not stop a FIFO, and a `read` on one wedges the unattended hook). A refused ledger read folds as *empty* and warns; a refused write errors. Two independent axes per entry: `decision` (`unreviewed|deferred|skipped|harvested`) and `stage` (`collected|indexed|compressed`); never collapse them. An entry at `compressed` is drained on read, loudly: the stage means "something else carries this now", and nothing does — a `conversations` row holds first prompt, summary and vectors, **not** the decision, memory ids or note — so the drain destroys a review record and warns naming every session. Nothing in this version writes `compressed`; the stage exists so the format need not change when something finally can carry it. Don't quietly `retain` it, and don't start writing it without giving the review record somewhere to go. Compaction rewrites the file at 4 lines per live entry, and must be **fold-preserving**: the snapshot line sorts at the entry's high-water mark (`at`) but restates the decision instant separately (`decided_at`), because the fold stamps `harvested_at` from `at` and a snapshot carrying only `at` silently moved every entry's "Recorded" time to its newest *mechanical* event — changing `ledger list`'s column and sort order, and the instant the 365-day window is measured from. Ordering by timestamp rather than file position also means a backwards clock can make an append lose the fold; `mark_harvested` returns `MarkOutcome::superseded` (and warns) rather than reporting a review it just watched being discarded. A pre-0.11 `harvested_sessions.json` is migrated on first read and kept as `.migrated`. Session ids reach both from hook JSON and MCP arguments, so `is_valid_session_id` gates every path join.
- **`conversation_index.rs`** — the `conversations` table, one row per session, in the **root** project's existing `lancedb/` beside `memories` and `chunks`. Two vector columns and the split matters: `digest_vec` is always present and comes from the *deterministic* reduction (`ops::harvest::index_text`), `summary_vec` is nullable and comes from a curated summary. Never derive `digest_vec` from an agent-authored summary — that is exactly what would make `reindex --archive-only` meaningless, since an agent's prose is not regenerable by code. Search queries both columns and breaks an exact tie toward the summary. `ConversationIndex::open` **creates** the table, so a machine-wide search must gate on `ConversationIndex::exists` first or it leaves an empty table in every project it looked at. Policy — which sessions are due, what text is embedded, what a search may return — is `src/ops/harvest_index.rs`, never here.

  Two invariants this table paid for in defects. **(1) Every search narrowing is a prefilter, never a post-filter.** `since` is resolved to a session-id set (`ended_at` is an RFC 3339 *string*, so the comparison has to happen in Rust on parsed timestamps) and pushed into the vector query as `session_id IN/NOT IN (…)`, whichever list is shorter. Applied after the k-NN `limit` it returned *nothing* whenever `limit` older-but-nearer conversations outranked the match, and the caller then printed "no indexed conversation matched" — an assertion of absence it could not support. **(2) The vector width is fixed at table creation and is checked on every open.** Lance opens a table AS-IS, so a `[embeddings].dimensions` change otherwise surfaces only as an Arrow error on every `upsert` and every `search`, with the cause never named — and `reindex --archive-only`, the documented rebuild, went through that same `upsert`. `ensure_table` now fails at open naming the remediation; `ops::harvest_index::open_index_for_rebuild` is the remediation (read the curated summaries off, `drop_table`, recreate, re-attach); and `ConversationIndex::open_existing` is the width-*agnostic* handle the repair and `ledger rm`'s row deletion both need. A machine-wide search skips (and names) a project whose index will not open rather than failing the whole call.
- **Harvest provenance and pinning (`src/ops/harvest_pin.rs`).** A memory records the sessions it was extracted from in `Memory::source_sessions` — the hidden `<!-- engramdb -->` block of the `.md` file, plus a `source_sessions` column (schema 0.7.0). Written by `harvest mark <session> --memory <id>` on both front-ends, which is the one call that already names both halves, so the agent does nothing extra. **A field, not a join table**, for two reasons that are not preference: the schema migration rebuilds the memories table from the `.md` files (so a LanceDB-only relation is destroyed by the mechanism that adds columns, silently unpinning every copy), and memory files are committed and travel with a clone while `lancedb/` does not. Deliberately **not** in `Provenance` — that struct is replaced wholesale by `MemoryUpdate::provenance`, and `provenance.session_id` means the session that *authored* the memory, which for a harvest is a different session from the one it is about. Deliberately **not** on `MemoryUpdate` either: the harvest flow owns this field and pin release is its own confirmed operation.

  The link **pins** the transcript copy: `transcript_archive::prune_archives(.., pinned)` spares it under both limits, and the size budget is measured over the *unpinned* copies only — counting pinned bytes toward the cap would evict every unpinned copy to make room for files it may not touch. Over-budget pinned bytes are *shown* (`doctor`, `harvest ledger prune`), never enforced. Release is `harvest ledger rm <id> --unpin`, which `--force` alone does not grant.

  **A caller that cannot enumerate pins must not prune.** An unknown pin is indistinguishable from an absent one right up until the transcript is gone, so the SessionEnd sweep skips the whole pass with a warning when the scope or a store will not resolve, and the CLI propagates the error. `ops::harvest_pin::evidence_links` walks every store in the `SessionScope`, deduped **by project id, never by path spelling**. `StorageError::NotInitialized` is *not* on its own a licence to skip a path: `MemoryStore::open` returns it for any `dir` whose `.engramdb/` does not stat, which covers both a git worktree with no store of its own (a real "no pins here") and a linked sub-project that was moved, deleted, or is on an unmounted volume (pins unknown) — and `session_scope` deliberately keeps registered paths that no longer exist. The path's own readability separates the two; treating them alike let the sweep prune with an incomplete set.

  Doctor's Harvest subsection reports four things and none of them flips the exit code: pending-index sessions, ledger compaction pressure (`harvest_state::compaction_is_pending`, sharing `COMPACT_FACTOR` with the writer), **expired evidence**, and pinned bytes. Expired evidence must read as *expiry*, never as breakage — the memory is still true, its copy simply aged out or was never collected on this machine.
- **Two rules the harvest work paid for in defects, both general.** (1) **Never compare paths textually.** Go through `project_id::compute_project_id` or `std::fs::canonicalize` — never `==` on a `Path`. The shipped MCP entry is `serve --dir .`, so the invoking directory is literally `"."` while the registry holds the canonical absolute path; a relative `--dir`, a symlinked checkout, and `/tmp` → `/private/tmp` on macOS all do the same. Two separate defects came from `==`, one of which deadlocked that shipped configuration. (Which of the two helpers depends on the question: `compute_project_id` keys off the git remote first, so two checkouts of one repository share an id — use `canonicalize` when a genuine sub-project must stay distinct from its root, as `adopt_ledger` does.) (2) **A loss path the code does not declare is a bug.** `capped_events` and `skipped_records` exist because the digest claimed a completeness it did not have; the ledger drain warns per session rather than dropping quietly; compaction's one microsecond-wide race is written down in `maybe_compact`'s doc comment. Anything that can silently drop a record must say so, in the doc comment and at runtime.
- **`worktree.rs`** — when invoked inside a git worktree, `cli::run` transparently routes ops to the **main** worktree's project and registers the worktree as a sub-project. Init/serve/completions/setup/daemon are exempt because they own their own behavior. Don't bypass `resolve_project_root` for normal commands.
- **`manifest.rs` + `EmbeddingFingerprint`** — each store records `model_id()` and dimensions for its embeddings. On open, `expected_embedding_fingerprint(config)` is compared to the live provider; mismatches surface as a `doctor`/warning saying "run `engramdb reindex --embeddings-only`". The fingerprint table and the provider-resolver share **one** `provider_specs` map in `ops/mod.rs` — this unification is intentional (preventing silent vector corruption) and changes to providers must be added in that single map.

### Index currency (content and embed digests)

Every index row records **what it was built from**, and every memory's vectors
record **what they were embedded from**. These are separate digests because
they answer separate questions and change independently.

- **`content_sha256` / `content_len`** (memories table, schema 0.8.0) — a
  SHA-256 over the `.md` file's line-ending-normalized bytes, plus its raw
  length. Stamped from the exact string the write path is about to
  `atomic_write`. **Never hash a re-serialization of a parsed memory**: a file
  written by an older binary need not round-trip to identical bytes, so that
  would mark it permanently dirty and no currency check would ever settle.
- **`embed_sha256`** (chunks table) — salted with the chunk texts, the model
  id, the dimensions, the composition and the chunk window, so an equal digest
  means re-embedding would produce identical vectors. It rides the *same* write
  as the vectors it describes, which is what makes it atomic with them.

Three surfaces read them, at deliberately different costs. `check_staleness`
runs on **every** `query`/`list`/`get` and is tiered by
`[index].staleness_check` (`counts` | `size` | `content`, default `size`) —
see `crates/engram-storage/src/staleness.rs`. `doctor` and `stats` hash every
file. `reindex --dry-run` hashes files *and* recomputes every would-be
embedding input; it is the only surface that can report stale **vectors**,
because that needs a live provider and no doctor path builds an engine.

**`reindex` skips a memory whose `embed_sha256` still matches**, which makes it
incremental. Two consequences to keep in mind:

- **Any change that alters the vectors must alter the digest.** Model, width,
  composition and chunk window are all salted in, so those are covered. A
  change to the *chunking algorithm* or to `embedding_texts`' composition that
  keeps the same inputs is **not** — it silently keeps stale vectors. Treat
  such a change like a schema bump: it needs `--force` in the release notes, or
  a new salt in `embed_digest`.
- **A repair must pass `force`.** Skipping trusts the stamp, so `doctor --fix`
  and `projects repair` always force; a repair that trusts the stamp it is
  repairing is not a repair.

**`reindex --incremental` skips rows whose file is unchanged**, opt-in and off
by default. Measured at 56–72% faster on an unchanged store (100–2000 memories,
`examples/reindex_incremental_bench.rs`) — the parse, the stem derivation and
the row write are all real cost. It cannot reach 100%: deciding whether a file
changed means reading and hashing it, so both paths enumerate, read and hash
identically. It never skips enumeration or
duplicate-id resolution (that walk deletes the loser of a duplicate pair), it
reconciles deletions explicitly from the *full* row set rather than the digest
map (a digest-less row whose file is gone must still be removed), and it falls
back to a full rebuild when the schema or normalizer stamp is behind — those
mean the derivation changed even where the bytes did not. `indexed_ids` must
include skipped memories or the orphan-chunk prune deletes their vectors.

**Anything that rewrites memory files must refresh the index.** `migrate` and
`rollback` rewrite every file under the project lock; without a following
`store.reindex()` (lock dropped first — it is not reentrant) every row is
drifted and every query warns, for a rewrite that changed no memory's meaning.

### Retrieval & scoring

- **`src/retrieval/engine.rs`** — the `RetrievalEngine` runs queries in two modes: `Filter` (narrow by query/path/logical/tags, query signal required) and `Rank` (rank everything by relevance to a context). Pipeline: index-level filter → optional vector search via LanceDB → composite scoring → optional cross-encoder rerank.
- **`src/scoring/`** — composite score formula depends on mode (see `scoring/mod.rs` doc-comment). Final = `base * scope_multiplier * trust_multiplier * situation_multiplier * supports_multiplier * usage_multiplier - challenge_penalty - contradicts_penalty`, clamped to `[0,1]`. Decay strategies are `None | Linear | Exponential | Step`.
- **Graph and usage signals (`src/retrieval/signals.rs`), every knob off by default.** `[retrieval.scoring]` `contradicts_penalty` (flat, once, for a *confirmed* `contradicts` edge to a *live* memory — exists, not invalidated, not expired; both ends of an undirected contradiction pay; proposed edges never count; a reviewer's direction is a `supersedes` edge, whose target is invalidated and hidden, nothing extra), `supports_boost` (≤ 0.1, `1 + b·min(n,3)` for live confirmed **incoming** `supports`), `usage_weight` (≤ 0.2, `1 + α·min(3, ρ·ln(1 + fetched + 0.3·injected_sessions))` with exposure ratio `ρ = min(1, (fetched+1)/(injected+returned+1))`: injection and a query answer are the engine's own choice, so a shown-never-opened memory's term stays under ~0.17 however often it is shown). With `contradicts_penalty` on, the penalty also counts against the scope-only gate, so both ends of a contradiction can drop under the rank threshold and the hooks then inject *neither* — documented in configuration.md/links.md as a consequence of the knob, deliberately not exempted. They reach `composite_score` as `ScoringContext::signals` (`ScoreSignals`), which the engine attaches **only when a knob is on — off means no lookup at all**, and multiplying by 1.0 / subtracting 0.0 is bit-exact, pinned by `graph_signal_tests::default_config_ranking_is_unchanged_on_graph_fixture` against bits captured before the knobs existed. Cost with a knob on: one `edges` query for the whole candidate set (`MemoryStore::edges_touching_any`: an `IN` list ≤ 500 ids, else one full scan) + one liveness lookup for the far ends; usage via the side-effect-free `load_current_usage`, cached **process-wide per store** for 30 s (`UsageCache` is a handle on a static map: every front end builds a fresh engine per call, so a per-engine cache was cold on every query). `signals::lookup_counts` counts edge/usage reads so `default_config_reads_no_edges_or_usage` can prove a default config looks nothing up. Any read failure = no signal, never an error; cross-store edges carry no signal (an unknown end is not evidence). **One-hop `expand_links`** (`RetrievalQuery::expand_links`, CLI `--expand-links [N]`, MCP `expand_links`, config `[retrieval].expand_links`, ≤ 20) follows confirmed same-store `supports`/`derived_from`/`related_to` from non-fallback hits; a neighbour must be in the **already-filtered candidate set** (so every hard filter — type, tags, class, criticality, expiry, validity, filter-mode scope — applies), scores `hit·expand_links_decay·own_situation − own challenge − own contradicts` (or its own query score when it had one and that is higher), keeps its own breakdown (so `contradicted_by` survives), carries `ScoreBreakdown::via`, and is added on top of `max_results` (`total` counts it once — a neighbour pulled back from the cut tail was already counted). `record_returned` skips `via` results (they did not survive ranking, so they must not feed promotion). The fan-in keeps that: `truncate_keeping_expansions` instead of `truncate`, `drop_orphaned_expansions` after the audience filter so a neighbour reached through a hidden hit never names it, `cap_expansions` to N per *query* (each store expanded N on its own), and cross-store equalization reranks the direct hits only, re-attaching neighbours of the survivors capped at their hit's new score (`reattach_expansions`). CLI `--expand-links` is `require_equals`, so a word after the bare flag stays the positional query. Hooks and the MCP `memory://context`/prompt surfaces pass `expand_links: Some(0)`. Eval + latency: `examples/graph_scoring_eval.rs`.
- **`src/scope/`** — physical (file path with depth-decay) + logical (dot-notation hierarchy, max bonus 0.3). Combined score is capped at 1.0.
- **`crates/engram-models/src/embeddings/`** — `EmbeddingProvider` trait, implemented by `OnnxProvider` (fastembed; default, gated by `onnxruntime`) and `OllamaProvider` (gated by `ollama`). The `model_id()` method is what gets persisted to the manifest — distinct fp32 vs int8 IDs are required so quantization swaps are detected. A pure-Rust `tract` backend used to sit alongside these for Intel Mac; it was removed once the runtime became separately installed, and `EmbeddingBackend` keeps a `"tract"` serde alias so old configs still load.
- **`crates/engram-models/src/nli/onnx.rs`** + **`crates/engram-models/src/rerank.rs`** — optional ONNX NLI for contradiction detection (`challenge` flow) and a cross-encoder reranker (BGE family by default). Both are loaded only when `[nli].enabled` / `[rerank].enabled` are true in `config.toml`. The reranker's `Reranker` trait and its `fastembed` loader (`LocalReranker::load`) live in `engram-models` next to the embedding/NLI/T5 loaders (so the core `engramdb` crate carries **no** direct `fastembed` dep); `src/retrieval/reranker.rs` is a thin re-export keeping `crate::retrieval::reranker::{Reranker, RerankScore, LocalReranker}` resolving for the engine, `ops`, and the daemon's `RemoteReranker`.

### Shared embedding daemon (`src/daemon/`)

stdio MCP is one process per agent session, so without coordination every concurrent Claude Code session would load its own copy of the embedding (and optional NLI/reranker) models — hundreds of MB and a ~240ms ONNX init each.

- **`[daemon]` is global, never per project.** The daemon is one process shared by every project and session of a user, so its settings come only from the global config file `<global_config_dir>/config.toml` (`engram_storage::paths::global_config_path`, honoring `ENGRAMDB_CONFIG_DIR`; type `engram_types::GlobalConfig`, loaded by `engram_storage::config::load_global_config_or_default`). **Every** `[daemon]` read goes through that loader: the client resolve path, the MCP heartbeat, `cli_daemon_policy`, `daemon run/status/stop/restart`, `doctor`'s `check_daemon()` and `stats --daemon`. A project's `.engramdb/config.toml` may still contain `[daemon]` — it parses into `EngramConfig::legacy_daemon` (raw `toml::Table`, deliberately not a `DaemonConfig`, so nothing can read it as settings), the loader warns once per path naming each key and the global file, and `doctor`'s "Config file" check reports it as a Warn. When `[daemon]` was per project, the first spawner decided the idle timeout for everyone, each session's heartbeat came from its own project (so it could ping slower than the daemon reaped), and two `socket_path` values meant two daemons. `enabled` / `use_for_cli` are global too; the per-session opt-out is `--in-process` / `ENGRAMDB_IN_PROCESS`.
- **The daemon reads a project directory for exactly one op: `Hook`.** Model ops still carry their `ModelSelection` and never read a project (the rule protocol 5 established, for the reason below). `Hook` is different by nature — running a hook *is* reading the project's store — and it is acceptable because engramdb is a single-user tool and this crosses no privilege boundary: the socket folder is 0700, `SO_PEERCRED` admits only the daemon's own uid, and that uid can already read every project it names. Keep model selection out of the `Hook` path's reach: the hook executor resolves the project's config itself and asks the daemon's `ProviderCache` for that config's bundle.
- **Model selection is per project and travels in the request.** Protocol 5 replaced `DaemonRequest { dir, backend }` with `models: Option<ModelSelection>` (resolved backend + the `[embeddings]`/`[nli]`/`[rerank]`/`[title]` sections — exactly what `model_demands` reads). The daemon builds its per-model keys and pool-size demands from those fields and **never reads a project directory** (the old `ConfigCache` that loaded `<req.dir>/.engramdb/config.toml` is gone). `DaemonRequest`'s hand-written `Serialize` still writes an always-empty `dir`: a v4 daemon's request type requires it, and without it that daemon cannot parse our `Ping`, never answers with its old version, and is never evicted (`v4_daemon_can_parse_a_v5_ping`). Don't remove it while v4 daemons can still be running. `engine_for_project`'s one-session pool is `InProcessFallback::SequentialPool`, applied to the in-process load only, so the daemon still gets the project's own `pool_size` and serves those calls from the shared models.
- **`daemon/server.rs`** runs a Unix-domain-socket server that loads each model once machine-wide and serves inference. **Auto-spawned on demand** when the global `[daemon].enabled = true` (default); race-coordinated by an advisory file lock. The spawner passes only `--socket`; the daemon reads `idle_timeout_secs` from the global config itself (`--idle-timeout` survives for tests and an explicit `daemon restart --idle-timeout`). Its idle watchdog exits the process after `idle_timeout_secs` with no activity **and** no in-flight connections. Each served request (including `Ping`) refreshes `last_activity`, so heartbeat pings alone keep it resident.
- **`daemon::DaemonCell` + heartbeat (self-heal + session-aware idle).** Provider resolution for both CLI and MCP goes through the shared `daemon::resolve_providers` / `resolve_providers_with` (`src/daemon/resolve.rs` — it lives under `daemon`, not `ops`, because it necessarily reaches daemon internals and `ops` must never depend on `daemon`), backed by a re-resolvable `daemon::DaemonCell` that **replaced the MCP server's old process-lifetime `OnceCell`** (which cached a `None` failure forever). The cell health-checks a cached handle on each resolve and re-spawns a dead daemon — rate-limited to one spawn per `idle/3` window, but only *failed* spawns consume the window (a confirmed-successful spawn resets the timer). Each `serve` process also runs `spawn_daemon_heartbeat`: a background task that resolves via the cell every `daemon::heartbeat_interval(idle)` = `max(30s, idle/3)`, with `idle` from the same global config the daemon reaps on (so `DaemonConfig::validate`'s `>= 60` floor really guarantees two pings per idle window); each resolve sends a `Ping` that (a) keeps the daemon alive while any session is connected and (b) re-spawns it if it died. So a live MCP session **self-heals** instead of degrading to in-process for its lifetime, and the daemon reaps only after the **last** session disconnects. `DaemonPolicy` (`ConnectOrSpawn | ConnectOnly | InProcess`) expresses the per-front-end difference: MCP uses `ConnectOrSpawn`; the CLI uses `ConnectOnly` by default (opt-in via `[daemon].use_for_cli`, default `true`; `--in-process`/`ENGRAMDB_IN_PROCESS` forces local; `--spawn-daemon` promotes to `ConnectOrSpawn`). The MCP server's daemon branch is still compiled out under `#[cfg(test)]`; daemon-path coverage lives in `src/daemon/tests.rs`.
- **`daemon/remote.rs`** wires `EmbeddingProvider` / `NliProvider` / `Reranker` trait impls that call the daemon over the socket — so the MCP server uses identical seams whether models are local or remote.
- **`daemon/metrics.rs` + persistence** — request metrics are persisted to the global store's LanceDB so `engramdb stats --daemon` reports cumulative figures across restarts (and even when no daemon is running). Heartbeat ping stats (`ping_count` / `last_ping_secs_ago` in `DaemonStatus`, rendered as `pings: N (last Xs ago)`) are **in-memory only** — current daemon, not persisted. `PROTOCOL_VERSION` is `"6"` (`4` added `Pong.build`; `5` replaced the request's `dir` with `ModelSelection`; `6` added `DaemonOp::Hook` and `DaemonOp::Version`). A client evicts a provably *older* daemon (protocol or build) with `Shutdown` and spawns a current one; a newer daemon is left alone and the client falls back to in-process.
- **Socket resolution** (`daemon/mod.rs::resolve_socket`) has fixed precedence: `--socket` flag → `ENGRAMDB_DAEMON_SOCKET` env → **global** `[daemon].socket_path` → `default_daemon_dir()/daemon.sock` (`$XDG_RUNTIME_DIR/engramdb`, else `<cache>/engramdb/daemon` — a dedicated leaf, because `<cache>/engramdb` is shared with the model cache — else `/tmp/engramdb-<uid>`). **Every** client/server site must use this helper so they agree on the socket.
- **One private daemon folder.** The socket's parent (`daemon::daemon_dir_for`) holds the socket, the `daemon.reclaim.lock` and `daemon.log` (`daemon::daemon_log_path(socket)` — moved out of the data dir; under `$XDG_RUNTIME_DIR` it is cleared on logout, acceptable for a "why did the last spawn fail" log). `transport::prepare_daemon_dir` creates it 0700, or **refuses** (bind and log open alike) when it exists with another owner, group/other bits, or is not a directory — it never chmods an existing folder. A bare relative socket (`d.sock`) maps to `.`, so the current directory gets the same check rather than being skipped. `doctor` runs the read-only `transport::daemon_dir_problem` and reports a refused folder as a Fail: like an occupied socket, it is not self-correcting. An overridden socket moves the whole folder, which is what keeps tests isolated. **Tests that bind a socket must use `daemon::private_tempdir()`, not `TempDir::new()`**: `tempfile` creates directories with the umask default (0755), which the transport now refuses.
- **A spawned daemon starts from an empty environment** (`daemon::client::spawn_command` → `env_clear` + `daemon_env`'s allowlist: identity, `PATH`, locale/temp, `ENGRAMDB_*` minus `ENGRAMDB_IN_PROCESS`, `XDG_*`, ORT/loader paths, `RUST_LOG`, `CLAUDE_CONFIG_DIR`, `OLLAMA_HOST`, proxies/certs, Windows system vars). It outlives the session that spawned it and runs every session's hooks, so it must not carry one session's `GIT_DIR`, secrets or tool settings. **A new env var the daemon (or any hook) reads must be added to `DAEMON_ENV_KEEP`**, or it silently differs between the in-process and daemon paths. A hook runs with the *daemon's* environment, so every variable that changes where a hook reads or writes (`ENGRAMDB_DATA_DIR`, `CLAUDE_CONFIG_DIR`, `HOME`, …) is also in `daemon::hooks::HOOK_ENV_KEYS`: the client sends its values with the `Hook` op and the daemon refuses (→ in-process) when its own differ. Add a new one there too. A manual `engramdb daemon run` keeps the shell's environment.
- **Graceful fallback** is the contract: if the daemon is disabled or unreachable, MCP **and** the CLI load models in-process exactly as before. Daemon failures must never break operations.
- **Models are leased, not kept forever.** The daemon knows model selections, not projects, so "closing a project" is a lease that stops being renewed: each MCP heartbeat sends a `Ping` carrying its project's `ModelSelection` (`DaemonHandle::renew_lease`), which `ProviderCache::touch`es every model that selection uses, at its pool size, and **never loads one**. A sweeper in `run_daemon_with` unloads every model unused and unleased for `DaemonOptions::bundle_idle_timeout` (= `idle_timeout_secs` in production), shrinks pools whose largest request expired, and calls glibc `malloc_trim(0)` whenever `ProviderCache::take_released` reports an unload or a replaced pool, without which RSS stays near its peak after an unload. `run_daemon_with` also fixes glibc's `M_MMAP_THRESHOLD` at 256 KiB (`fix_mmap_threshold`): glibc otherwise *raises* the threshold each time an mmapped block is freed, so after the first unload the next bundle's weights and arenas came from the heap, fragmented, and `malloc_trim` could not return them (heap after a close climbed 19 → ~105 MiB; with the fix it holds at ~20 MiB, at no measured latency cost). `M_ARENA_MAX` was tried and did not help. Two races this paid for: `evict_idle` keeps a model any caller still holds (`ModelHandle::in_use` — an `Arc` count above the cache's own), and `dispatch` re-`touch`es after serving, because `get` stamps at request *start* and a request longer than the window otherwise left the model looking idle the instant it was released. Before this, every selection ever served stayed resident while any session's heartbeat kept the daemon alive — days.
- **ONNX runs are capped at `MAX_TEXTS_PER_RUN` (8) texts** in `OnnxProvider::embed_batch`, and the reranker at `MAX_DOCS_PER_RUN` (4) query-document pairs (`LocalReranker`, whose fastembed default batch was 256 pairs of up to 512 tokens). ORT's CPU arena grows to the largest run a session served and never shrinks, and fastembed runs a dynamically quantized model's whole input as one batch, so a single 64-chunk request (one `EMBED_BATCH_CHUNK`) left the daemon at ~3.4 GiB, per pool session. Don't remove the cap or hand fastembed a whole request. Side effect: a memory with more than 8 chunks now embeds in runs of 8, so its vectors differ at rounding level from the one-batch run that produced the stored ones (dynamic quantization is batch-dependent); `embed_digest` is not salted for this, which is deliberate — queries always embedded alone, so stored vectors were never batch-consistent with them.
- **`benches/memory_footprint.rs`** measures the daemon's RSS (as a child process) and the MCP store path's across request churn, request sizes, shared-config projects and open/close cycles. Not Criterion; `cargo bench --bench memory_footprint -- --check` exits 1 on a failed bound. Run it after touching `ProviderCache`, the daemon's request path, or any ONNX session setup. It reports the anonymous (heap) RSS on Linux separately: the ONNX Runtime library's code pages (~78 MiB file-backed) stay mapped after the first load and are not something a close can return.

### Claude Code integration (`crates/engram-cli/src/commands/hook.rs`, `setup.rs`)

- Six `engramdb hook <event>` subcommands are what Claude Code invokes: `pre-tool-use`, `session-start`, `user-prompt-submit`, `post-tool-use`, `session-end`, `pre-compact`. They read hook event JSON from stdin; the context-injecting ones emit `additionalContext` JSON to stdout, and `SESSION_CONTEXT_BUDGET` (2000 chars) caps the SessionStart injection. A **seventh** clap variant, `HookCommand::Unknown`, is a deliberate catch-all: the wiring in `plugin.json`/`settings.json` updates independently of the binary, and an unrecognized subcommand name would otherwise exit 2 — which Claude Code treats as a *blocking* hook error, breaking every prompt in the session. Every handler fails open; keep it that way.
- **`session-end` is the one that writes**, and it is no longer housekeeping-only. In order: clear the session→task mapping, optionally run the `[epistemic].demote_on_session_end` demotion, then `archive_ending_session` — copy the transcript (zstd, under the **root** project's `transcripts/`), append the ledger line via `set_archive` (which creates an `Unreviewed` entry), and run the retention sweep, whose evicted files are cleared back out of the ledger with `clear_archive_refs`. Each step is best-effort and swallowed *except* the pin enumeration, which skips the whole sweep rather than pruning with an incomplete set. It bails early unless `manifest.toml` or `memories/` exists, because the plugin registers hooks machine-wide and every directory Claude Code is started in would otherwise collect state. Ordering is load-bearing: archiving is the slow step and goes last so a hook timeout cannot cost the mapping clear.
- **UserPromptSubmit searches every prompt; there is no skip decision.** A trained skip gate was evaluated and parked (`docs/contributors/prompt-intent-eval.md`): no model was safe enough, and a search costs milliseconds. When the prompt's own Filter query leaves room, a second one on the tail of the agent's previous message (`last_assistant_text` reads only the transcript's last 1 MiB) fills it; the prompt's matches always rank first. The situation comes from `engramdb::prompt_intent`'s embedding classifier: the model of a daemon that `resolve_daemon_providers` finds **already running** (it never spawns one), else the embedding model alone loaded in the hook process (NLI, reranker and T5 switched off first; measured +~290 ms per prompt in release, against +~55 ms through a running daemon — acceptable because UserPromptSubmit fires per prompt rather than per tool call), else `keyword_situation`. `classify_once` embeds the seeds and the prompt in one batch and keeps nothing, so there is no seed cache to go stale; `PrototypeParams::seeds_per_class` is the cost knob. Unit tests use `SituationModel::KeywordOnly` / `Provider`, never `DaemonOrInProcess`, so they cannot reach a daemon or load a model on the developer's machine.
- **Hooks run in the daemon when one is up** (`src/daemon/hooks.rs`, protocol 6). `engramdb hook <event>` reads stdin and, before any project work of its own (registry, worktree routing, config), offers the event to an **already-running** daemon (never spawned for a hook) as `DaemonOp::Hook { call, dir, stdin }`, on one connection that first sends `DaemonOp::Version` (answered with a `Pong`, but not counted as a heartbeat ping) so a hook is only ever sent to a protocol-6 daemon. Measured on release (p50 wall, 100 memories, compacted): `pre-tool-use` 28.9 → 18.9 ms, `post-tool-use` 19.1 → 15.0, `session-start` 20.6 → 16.6, `user-prompt-submit` 337 → 77; `pre-compact` / `session-end` unchanged (~9 ms, all start-up). The handlers live in this crate, so `daemon run` injects them as a `HookExecutor` (`DaemonHookExecutor`): it does the worktree routing and config load itself, runs `execute_hook` against a warm per-project `StoreCache` (max 16, 10 min idle, reopened when `config.toml`/`manifest.toml` change; freshness does not depend on it, since every LanceDB call reopens its table), and gives `user-prompt-submit` the daemon's own embedding model (only that one: the executor switches NLI, reranker and T5 off before `ProviderCache::get`, which otherwise loads every model a config enables). The store cache opens a store *outside* its lock, because an open can run a schema migration. **The fallback rule is about side effects:** run in-process only when the daemon provably did not run the hook (`HookDelegation::NotSent`: not listening, older protocol or build, no hook runner, a different environment, write failed); when the request was sent and the reply was lost (`Lost`), print nothing and do not retry — the daemon may have run it, and a second run would repeat the "already shown" record or the SessionEnd archive. `--in-process` / `ENGRAMDB_IN_PROCESS` / global `[daemon].enabled = false` or `use_for_cli = false` keep hooks in-process (a hook is a CLI invocation) (the tier-2 fixture sets the env var, so its snapshots never reach a daemon). Every handler is one function, `execute_hook(call, dir, stdin, env) -> Option<String>`, that neither reads stdin nor prints; `HookEnv` carries what differs between the two paths (`StoreSource::{Fresh, Cached}`, the `SituationModel`). **SessionEnd runs on its own thread with its own runtime on both paths**: its future fails rustc's higher-ranked `Send` check somewhere inside the harvest helpers, and it is the slow hook. Don't "simplify" that back inline — the daemon path needs a `Send` future.
- **Hook call stats** (`engram_storage::telemetry::{hooks, hook_events}`). Two writers, one long-term table. The daemon buffers each hook it serves per project and writes the per-project `hook_events` LanceDB table (path `daemon`) every 60 s, at 1,024 events, and on every shutdown path (`Ctx::persist` flushes; a `SIGKILL` loses at most one interval). A hook that runs in its own process appends one JSON line (`id`, `ts`, `hook`, `ms`, `ok`, `path`, `session_id`) to `.engramdb/state/hook_stats.jsonl` through `state_file` — a LanceDB write per hook would cost milliseconds and a fragment on every Read/Edit — and `drain_to_table` later moves those lines into `hook_events`: claim by rename, short grace for in-flight writers, `merge_insert` on `id`, delete only after the insert succeeded, so a crash costs a harmless re-insert. Drainers: the daemon (throttled, after serving a project), plus `gc` and the CLI maintenance pass via `ops::maintain_hook_events` for users without a daemon. `hook_events` is deliberately **not** `stats_events`: hook rows would crowd tool rows out of the 50,000-row startup replay, and old binaries never read a new table. `stats` (CLI + MCP) reads `load_combined_summary` = table + not-yet-drained JSONL (claimed files are never read, so nothing counts twice); counts/errors/avg over `[stats].retention_days`, p50/p95/p99 over the newest 10,000 samples per (hook, path), with a per-path breakdown. The clock starts at `cli::run` entry (in-process) or around the handler (daemon); process start-up is invisible to both. Only initialized stores record (same `manifest.toml`/`memories/` test as SessionEnd), `HookCommand::Unknown` never records, and every loss path (rotation race, drain grace, lost replies, a killed daemon) is declared in the module docs.
- **Per-memory usage events** (`engram_storage::telemetry::{usage, memory_events, jsonl_log}`, policy in `src/ops/usage.rs`). Same JSONL-then-drain life cycle as hook stats, and now the *same code*: `jsonl_log::JsonlLog` owns append/rotate/claim-by-rename/grace/delete-after-insert for both logs (`hooks.rs` was refactored onto it), so their declared loss paths cannot drift. Lines go to `.engramdb/state/memory_events.jsonl` via `state_file`, drain into the per-project `memory_events` table (`merge_insert` on the uuid-v7 `id`), and a `memory_usage` rollup holds per-memory `base` counts plus a `watermark`: totals = `base` + raw events at or after it. The retention prune (`[stats].retention_days`) writes the rollup *first*, then deletes raw rows, so a crash between the two re-counts nothing; across a prune distinct-session counts are summed (an over-count, declared), and a late event older than the watermark is not counted (declared). **Every write to either table holds the per-store `memory_usage.lock`** (beside `lancedb/`): the insert *and* its refresh, the prune, and `reconcile_rollup`. Each rewrites whole rollup rows, and a refresh that read a row before a prune folded it would write `base = 0` back over the fold — the raw rows are already gone, so the counts are lost for good (`a_prune_cannot_interleave_with_a_refresh` pins it via a `#[cfg(test)]` pause point). Under the lock a refresh copies `base`/`watermark` through from its own read. Lock order is drain claim lock → rollup lock, never the reverse. Scans stream into per-memory accumulators (`for_each_event`), never a `Vec` of events: the prune reads only `ts < cutoff` and then the affected memories' recent window in `IN (…)` chunks of `MAX_IN_LIST`. The cutoff is truncated to µs once (`trunc_us`) because `ts_literal` prints µs and a nanosecond Rust cutoff double-counted the boundary event, and a watermark never passes the newest folded event + 1 µs (a forward clock jump at prune time cannot hide later events). `reconcile_rollup` (maintenance pass, after the prune) repairs rows a failed refresh left lagging. Kinds and surfaces are **strings on disk** (`EventRow`): a newer binary's line is stored verbatim and only left out of counts — a strict enum parse made the drain delete it as unreadable. Reads (`load_usage`, `load_current_usage`, `load_daily_series`, `returned_sessions`, `ops::memory_usage_report_in`) go through `persistence::connect_existing` + `open_existing` and **create nothing** (no dir, table, lock or migration) and **return errors, never silent zeros**; `top_used` reads `load_current_usage` (rollup + undrained JSONL, session counts an upper bound) — that is the dashboard's read API. Read signals are three kinds that are **never summed** — `returned` (CLI/MCP `query`, the MCP `memory://context` resource and `memory-session-start` prompt; written per owning store; the CLI attaches `CLAUDE_SESSION_ID`/`MCP_SESSION_ID` when set, and sessionless events never count for promotion), `injected` (hooks, at `record_shown`), `fetched` (CLI/MCP `get` front-ends only, so internal gets don't inflate it); write kinds (`created/updated/challenged/resolved/verified/promoted/merged/deleted`, and `linked` for every edge write — the proposers from `Surface::Maintenance`, the dashboard review from `Surface::Dashboard`) are recorded **in `ops`** by wrappers that take a trailing `Surface` (`ops::create_memory(.., Surface::Cli)`; the `*_unrecorded` inner fns are what other ops compose), never by the front-ends. NLI auto-challenges and `list`/`discover` are not recorded. An event for a group/global memory goes to the **owning** store's log (`QueryResult` fan-in carries `owners`), which is why `persistence::lancedb_root` now maps `__g_` ids to `groups/<id>/lancedb`. Gated on `[stats].enabled` and on an initialized store, like hook stats. On the daemon hook path the handler cannot append (side effects must be the daemon's), so `HookEnv.usage` is `UsageSink::Collect` and the events ride `HookRun.usage_events` into `HookTelemetry`'s per-store buffer, flushed with hook events; drainers sit beside `maintain_hook_events` (daemon, `gc`, CLI maintenance via `ops::maintain_memory_events`, which also drains subscribed groups and global, each under the *shared store's own* `[stats]`; a group nobody subscribes to is drained only by `gc` on it — declared). **Promotion reads `returned` usage events** unioned with the legacy `stats_events` Retrieval rows (the engine no longer writes those). No schema bump: both tables are created lazily and are not derived from `.md` files, the `hook_events` precedent. `Memory::accessed_at` / `touch` are deprecated in doc only. Surfaced by `stats --memory <id>` and `stats --top N --by fetched|injected|returned` (MCP `stats` `memory_id` / `top` / `by`); a memory with no read events is excluded from top-N rather than listed at zero.
- **The Bash retry prompt.** `post-tool-use` also serves `PostToolUseFailure`, both on matcher `Bash`: a failed command is recorded by a key (the script or program it runs, ignoring `VAR=` prefixes, wrappers, flags and probes such as `ls`/`cat`/`grep`) in `.engramdb/state/bash_retry/<session>` (`engram_storage::bash_retry`), and when a later run of the same key succeeds the hook asks once to save the cause. A pipeline counts as failed only on unmistakable failure output, because its exit status is the last stage's. It writes state, so it bails in a directory that was never `init`ed, like SessionEnd.
- `engramdb setup` writes the hook + MCP entries into `settings.json` (or under `.claude/` for project scope). The `.claude-plugin/` directory is the marketplace plugin that does the same thing automatically.
- **`commands/`** holds the slash commands the plugin ships — `commands/reflect.md` (`/engram:reflect`, mine the session you are *in*) and `commands/harvest.md` (`/engram:harvest`, mine sessions that are already *over*). They are markdown prompt files, not code, so a hooks-only `engramdb setup` install does not get them. `harvest.md` is the agent-facing contract for the whole harvest flow: when it names a tool or a flag, that name has to still exist.

### Provider caching

`ProviderCache` (`src/ops/provider_cache.rs`) caches each **model** on its own, keyed by `ModelKey` — what identifies that model alone: the embedding model by resolved backend, provider and dimensions; NLI and the reranker by model name; T5 by itself. `get` assembles a project's `EngineProviders` from those shared entries. It used to key one whole *bundle* on every model-affecting field at once, so two projects differing in one setting (`[nli].enabled`, `[title].strategy`, a pool size) each loaded every model again, the embedding pool included.

- **Pools are shared at the largest demand, in powers of two.** Every request and lease records a *demand* (requested pool size → when). A pooled model (embeddings, T5) is loaded at `pool_class(largest live demand)` = next power of two, capped at the core count, so requests of 1, 2 and 3 share a pool of 4. A bigger demand grows the pool **in the background** (`spawn_resize`; the current pool keeps serving), and `evict_idle` shrinks it once the largest demand expires. A resize **rebuilds** the pool instead of adding sessions, because every session is built with `cores / pool_size` intra-op threads and mixing sizes oversubscribes the cores. NLI and the reranker are single sessions (demand `1`).
- **Entries are never removed from the map**, only emptied: removing one would race a caller that already holds the slot and is about to load into it, leaving a loaded model the cache no longer tracks. Each slot has its own async single-flight lock, so a slow T5 load never stalls an embedding lookup. A failed load is retried after `FAILED_LOAD_RETRY_AFTER`, per model.
- **Adding a model-affecting config field:** `model_demands` destructures all four model sections exhaustively, so the build fails until you decide whether the field is part of a model's identity (put it in `ModelKey`), a pool-size demand, or neither. If it lives outside the four sections `daemon::ModelSelection` carries, add it there too, or the daemon will key (and load) models without it. `provider_cache_key` is now only a signature built from `model_demands`, which the daemon tests use to prove a `ModelSelection` round-trips every field.
- **Resizes and releases are guarded.** A failed or short rebuild (a pool can come up with fewer sessions than asked for; `ModelLoader::load` reports the real size) backs off for `FAILED_LOAD_RETRY_AFTER` instead of being retried on every request. A rebuild re-checks the target before swapping and drops its pool if demand moved back meanwhile. Pools the cache lets go of are dropped on a blocking thread and counted by `take_released` only once really freed (`retire` keeps a `Weak` per handle), so the daemon's trim never runs before an in-flight request has released a replaced pool. A resize briefly holds the old and the new pool at once.
- **The in-process MCP fallback has no sweeper**: demands there never expire, so pools grow but never shrink or unload — the same lifetime as the old per-bundle cache, which never evicted in-process either.
- **Tests never need a model:** `ProviderCache::with_loader` takes a `ModelLoader`; `provider_cache::test_support::FakeLoader` records every load (and can fail, cap the sessions it builds, or delay), and `daemon::server::run_daemon_with_cache` runs a daemon on such a cache.

## Model Downloads

All ML model downloads (embeddings, reranker, NLI) MUST cache to the same directory: `dirs::cache_dir() / "engramdb" / "models"` (see `storage::paths::model_cache_dir`).

- Fastembed models: use `TextInitOptions::new(model).with_cache_dir(cache_dir)` (`InitOptions` is a deprecated alias since fastembed 7)
- HuggingFace Hub models: use `ApiBuilder::new().with_cache_dir(cache_dir).build()`

Never use default cache locations (e.g., `~/.cache/huggingface/hub/`). The web-sandbox workaround above relies on this exact path layout.

## Memory (EngramDB)

This project uses EngramDB as a persistent memory store via MCP.

- **Before answering any project question** (conventions, workflows, architecture, tooling, "how do we..."), call `query` with `mode: "filter"` and a `query` of relevant keywords.
- **Before modifying files**, call `query` with `mode: "rank"` and the file `path` to surface known decisions, hazards, or conventions.
- **After discovering** important patterns, decisions, hazards, or conventions, store them with `create`.
- **When a decision or convention spans multiple related projects** (a monorepo family / a set of repos you're working on together on this machine), save it to a shared store instead of only the current project, so every relevant project surfaces it:
  - Write to a named group with `project: "group:<name>"` (set up once per project with `engramdb groups subscribe <name>` on the CLI; subscribed groups fan into a project's queries automatically). Use this for knowledge shared by a *specific set* of related repos.
  - Write to `project: "global"` for knowledge that applies *everywhere* (personal preferences, machine-wide conventions).
  - To share a *single* memory to an arbitrary subset of projects, set `audience` to their project/group ids on `create`/`update` (a group- or global-store write with `audience: [...]` surfaces only for the listed projects). Omit `audience` for whole-group visibility. Note: `audience` is advisory fan-in scoping, not a confidentiality boundary.
- **If you find contradictory information**, use `challenge` to flag the memory for review.
